Price lookup: code finds the price, the model only reads

Spencer Brimley · Python + PDF word positions + Ollama (Granite 4 Micro-H) · Oct 2026

At a glance

  • Problem: staff asked for vendor prices, by part number or by description, and the prices sat in 36 PDF price books.
  • What I built: a Python lookup over those books, with a screen in the ERP in front of it. Code found the row and did every calculation. A small local model read one page only when code could not find the answer.
  • The rule: the model reads; code decides. Anything the books did not answer was refused, not guessed.
  • Results: 35 of 36 test questions answered correctly and the last one flagged, scored by code. These are regression tests, not a held-out test (details below).
  • Status: write-up only. The ERP screen was deployed on 19 October 2026, but the business went back to paper before it came into regular use, so there are no usage numbers. The code was written on company time, so the employer may own it and there is no repository.

The problem

Our vendors publish their prices as PDF price books. The books are tables: a part number, a description or a size, and one or more prices. Someone who needed a price opened the right book and searched for the part. That is slow when you have the part number and slower when you only have a description such as a door type and size.

A wrong price is worse than a slow one, so I wanted a lookup that would rather refuse than guess.

What I built

The lookup ran on the purchasing PC, which has no GPU and 16 GB of RAM. In October 2026 I built a corpus from the 36 price books in scope: 1,250 pages with prices and 21,401 price records. A screen in the ERP asked a small Python service for an answer.

A question went through a list of routes, and the first route that could answer won:

  1. Refuse (code). If the question is about something the books cannot answer, such as what we paid last time or a vendor that is out of scope, the lookup said so instead of returning a neighbouring price.
  2. Part number (code). A part number went through our cross-reference table, or straight to its record in a book.
  3. Style name (code). A product family name returned the codes in that family.
  4. Stock (code). "Is this stocked?" was answered from a stock mark printed in the book. I read the mark by its position on the page.
  5. Policy page (code, with the model as a reader). A question about lead times or ordering went to the page that discusses it, and no price was asserted from that route.
  6. Description (code, with the model as a reader). A description was matched to one page by keyword search. Code then filtered that page's rows by size, after turning "3-0" or a foot mark into inches, and the model read the few rows left. Code did every calculation.

The ERP screen used only the routes that need no model. When a question fell through, it pointed to the likely pages and never showed a price written by a model. The two routes that used a model ran on the purchasing PC, where Granite 4 Micro-H, a small IBM model, ran through Ollama on the CPU.

A code often prints more than one price. In the corpus, 7,154 of the 21,401 records print more than one, and 1,021 of those print two different kinds of price, such as a list price and a net price. The kind is read from the page's own header band when the corpus is built. Someone could ask for a kind ("the net price of ..."), and that column was answered first. With no ask, the lookup answered the best-ranked kind and still showed the others, so nothing was hidden.

Results

  • Retrieval, 5 to 8 October 2026. On 17 descriptive questions (n = 17, a small sample), keyword search put the right catalog item first 13 times and embedding search 8 times.
  • Labelled columns. On 9 test questions, the same small model went from 5 to 9 correct after code labeled each price column on the page. Before that, every failure was the model taking the figure from the wrong column.
  • The reviewed question set, 8 October 2026. I reviewed 29 questions and wrote the right answer for each. The tool answered 28 correctly. The 29th was flagged because the question's own premise was wrong. Code did the scoring: every figure I had stated had to appear in the answer, and out-of-scope questions had to be refused.
  • The full set. Adding three stock-status and four which-price questions made 36. The tool answered 35 correctly and one was flagged, the same one.
  • What these numbers are. They are regression tests. I corrected the tool while I wrote the questions, so the tool was tuned against them, and no question was held out. They show that the fixes hold, not how it would do on a new set.

What went wrong

  • The text layer paired the wrong price. My first extraction used pdftotext's layout mode. Where a record spans several lines, it shifts the rows, so a code was paired with the next record's price. I found it when I reviewed the first set and three of the first ten answers were wrong. Reading word positions instead of the text layer reproduced all four corrections I had made. Every retrieval number I had measured before the fix was void, and I discarded them.
  • The model was not the failure. The first failures looked like model errors. The real cause was that the extraction threw away which column each figure came from. Once code labeled the columns, the same model got 9 of 9.
  • A row without its description was refused. The model correctly refused to price a bare code and price, because nothing said what the code was. The refusal was right and the context was wrong, so the model never saw a row without its description after that.
  • A policy question got prices. A question about a lead time was answered with price rows, because a price table's header literally read "factory lead time". That is why the policy page route exists and asserts no price.
  • One page, not three. With three pages in front of it, the model answered from the wrong one while two better pages went unread. Retrieving a single page fixed it.

A known limit

When two items of the same size sit on one page and the book prints no description beside each code, size cannot tell them apart, and the lookup could return the wrong one of the two. The books carry the names beside the product pictures, not in the text. I left it as a limit and did not paper over it.

The 60-second version

Our vendors' prices were in 36 PDF price books. I built a Python lookup over them. Code found the row, turned sizes into inches, picked the right price column and did every calculation. A small local model read one page only when a description did not match a code, and the lookup refused anything the books could not answer. It answered 35 of 36 test questions correctly, with one flagged. Those were regression tests, not a held-out set. The first extraction paired codes with the wrong prices, and finding that taught me to check the extraction before the model. The ERP screen was deployed on 19 October 2026, but the business went back to paper before it came into regular use.
