Bill checker: the model reads, code decides

Spencer Brimley · Python + pdftotext + QuickBooks Online + Baserow + Ollama · Oct to Nov 2026

At a glance

  • Problem: about 250 vendor bills a month arrived as PDFs and had to be checked against their purchase orders before they went into QuickBooks.
  • What I built: a Python tool that ran every morning on the purchasing PC. It read each bill, entered the bills that reconciled in QuickBooks, and put every price or quantity difference into a Bill Discrepancies table I worked through.
  • The rule: the model reads; code decides. A small local model answered narrow questions about the text, code checked every answer, and anything that failed went to a person instead of being guessed.
  • Results: 294 bills and credits entered between 9 October and 11 November 2026, and 95 discrepancy lines logged on 70 bills between 9 and 28 October 2026.
  • Status: write-up only. The code was written on company time, so the employer may own it and there is no repository.

The problem

About 250 vendor bills came in each month, as PDFs attached to emails. Each one had to be checked against its purchase order before it went into QuickBooks. Depending on the bill, checking the prices took a few minutes. It took longer when there was no PO to compare against, for example when an order had been phoned in, because then the bill had to be entered by hand.

A wrong bill entered is worse than a bill entered slowly. So I wanted a checker that would rather stop than guess.

What I built

A separate Python tool that ran every morning on the purchasing PC from Task Scheduler. It pulled the last 30 days of bill emails from Outlook, refreshed its copy of our QuickBooks bills and POs, and read each PDF. A bill whose lines added up to its printed total was entered in QuickBooks, or matched to the credit already there. Each price or quantity that differed from the PO went into a Bill Discrepancies table in our ERP as one line item. I worked through that table and contacted the vendor when it was warranted.

Anything the tool could not settle was held with a reason. Held items went out in one email a day to the sales inbox, and the PDFs stayed in a folder on the desktop for a person to handle.

Everything ran on our own machines. No cloud AI service saw a vendor document.

A sibling tool on the same PC answered price questions from vendor catalogs. Staff opened it from a price-lookup screen in the ERP, which went live on 19 October 2026 and was used 533 times by 13 November.

How it decides

The rule I built around: the model reads; code decides. A language model may answer a narrow question about text. Code checks every answer, and all the arithmetic happens in code.

  1. Read (code). The text layer of each PDF is read with pdftotext and parsed by a reader written for that vendor's layout. The model never retypes a table.
  2. Check the bill against itself (code). The lines must add up to the printed total. If they do not, the bill is held and nothing is entered.
  3. Match lines to the PO (code, with the model as a helper). Most lines matched on our SKU cross-reference. For lines that did not, a small local model was asked closed questions, such as which reference field on the bill is the PO number, or whether a price is per foot or per hundred feet. Code then checked the answer: a price basis has to reproduce the line total printed on the bill, and a PO link has to match exactly. An empty or failed answer counts as a reject, and that line goes to a person.
  4. Compare and write (code). Price and quantity differences go to Bill Discrepancies. Quantities are converted to the same unit first, because a PO in linear feet against a bill in pieces would invent differences that do not exist. Right before each QuickBooks write, the tool checks again that the bill number is not already there. If a run would enter more bills than a set limit, it stops and waits for a person.

Each vendor format needed its own handling: a label on one line with its value on the next, a credit that prints its amount with a trailing minus, spaces inside numbers, and two totals per invoice, one before the early-pay discount and one after.

Results

  • Daily runs. From 9 October to 11 November 2026 the tool entered 294 vendor bills and credits in QuickBooks: 146 in the first batch on 9 October, then 148 from the unattended daily run (128 bills and 20 credits). It covered the four vendors I had written readers for. Bills from other vendors went to a person.
  • Discrepancies. From 9 to 28 October 2026 it logged 95 discrepancy lines on 70 bills: 89 on price and 6 on quantity. By November, 91 were resolved and 4 were still open.
  • What it caught. One vendor's prices for insert cut-outs did not match our POs. Nobody knew how long that had been going on, and nobody else had caught it.
  • The model as a helper. In the reconciliation pass of 8 October 2026, over 172 bill lines, code matched 118 lines on the cross-reference alone. The model helped match 39 more, and code checked each one. On 15 lines the model's answer failed the check or came back empty, so those went to a person.
  • Why the model does not decide. In an October 2026 test on a synthetic PO and invoice pair, a small local model asked to compare the two documents answered "no discrepancies". The unit price had gone up 17.8%. Asked one narrow question at a time, the same model read the fields correctly.
  • How much the model was needed. On a batch of 23 real documents with clean text layers (October 2026), code alone resolved 12 of 12 documents and 11 of 12 PO links. The model was needed once, for a price column with no stated basis.
  • Price lookup. On 17 descriptive questions (n = 17, a small sample), keyword search put the right catalog item first 13 times and embedding search 8 times. On 9 test questions, the same small model went from 5 to 9 correct after code labeled each price column on the page. Before that, every failure was the model taking the figure from the wrong column. Tests run 5 to 8 October 2026.

What I tried and dropped

  • Letting the model give the verdict. Dropped after the 17.8% test. The model may read. It never answers "is this bill right?".
  • A document-conversion tool (Docling) for intake. The plain text layer was enough for every vendor in scope, because their bills are born digital, and it needs no model and no heavy dependency (8 October 2026).
  • Embeddings to match parts. On 236 real catalog items, similarity search put the exact size first only 23 to 27% of the time. It got the door type right every time. A 15% price change still scored as a perfect match, because the description had not changed. Embeddings can narrow a category, but a part with an identifier should be matched on the identifier.

What I'd change

  • Part numbers. Mapping a vendor's part number to our catalog was a separate step, so each new vendor still needed a reader written by hand. I would build the mapping into the checker so adding a vendor takes less code.
  • The drift counter. I tracked how often the model was needed per batch, because a rising count means a vendor reader has drifted. I would put that count on a dashboard so a drifting reader shows up early.

The 60-second version

About 250 vendor bills a month had to be checked against their POs before they went into QuickBooks. I built a Python tool that ran every morning. It read each PDF with code, entered the bills that added up and matched, and logged every price or quantity difference to a Bill Discrepancies table that I worked through. A small local model helped match lines the cross-reference missed, and code checked every answer it gave. Anything that did not check out was held for a person. From 9 October to 11 November 2026 it entered 294 bills and credits and logged 95 discrepancy lines. One of them showed that a vendor had been mispricing insert cut-outs for longer than anyone knew.
