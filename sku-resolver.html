SKU resolver: select the door, never compose the code

Spencer Brimley · Python, standard library only · Oct 2026

At a glance

  • Problem: staff wrote doors the way they speak, and every purchase order, worksheet and invoice needed the catalog SKU.
  • What I built: a Python package that reads a description into a spec (size, style, core, thickness, fire rating, how it hangs) and matches the spec against the doors the catalog already carries.
  • The rule: a SKU is never composed from text. It is only selected from the catalog, so the tool cannot invent a code that does not exist.
  • Results: checked against what was actually billed, 438 of 448 worksheet doors and 754 of 769 purchase orders agreed, measured in October 2026.
  • Status: write-up only. The code was written on company time, so the employer may own it and there is no repository.

The problem

A catalog names a door with a code. Nobody writes the code on a worksheet or a purchase order. People write things like "2-6 6-8 2-panel HC" or "3-0 8-0 1-pnl 1 3/4 20-min", and each of those has to become exactly one SKU, every time, for every person.

The same door was written a dozen ways. Prices, reorders and vendor matching all depended on someone remembering which way meant which door. A wrong SKU is worse than a blank one, because it shows up on an invoice months later.

What I built

A Python package of about 5,400 lines, with 115 unit tests, using only the standard library. It runs in three places:

  • the purchase-order workflow, where a PO line becomes a SKU for QuickBooks;
  • the worksheet pass, which wrote one row per worksheet line, with its SKU, into the ERP every few minutes;
  • the price lookup, when someone searched by description instead of by code.

It is read-only. It never wrote to the ERP, QuickBooks or the purchasing database itself. Other jobs took its answer and did the writing.

How it decides

  1. Read the spec. The description is parsed into width, height, style, core (hollow or solid), thickness, fire rating, and how it hangs (single, pair, bypass, pocket). Size is read from the written size, never from separate width or height columns that someone may have filled in differently. Words that do not change the slab, such as boring, prep or a magnetic catch, are noted and ignored.
  2. Match, do not compose. The spec is compared with every door in the catalog. A match needs every written word to be accounted for: it either selected the door, or it is a known word that does not change the slab.
  3. Say what happened. One of three answers, below.
AnswerMeaningWhat the next job may do
resolvedExactly one catalog door fits and every word was understood.Use the SKU.
needs_reviewSeveral doors fit, or one fits with words left over.Show the candidates to a person.
unresolvedNothing fits, the size or style could not be read, or the customer supplied the door.Leave the SKU blank.

A leftover word is the only sign that the writer meant a different door, so it is treated as a failure to be asked about. The middle answer exists because most real mistakes are not "no idea", they are "two plausible doors". Folding that into either of the other answers would throw away the shortlist and make a person start over.

On a worksheet, a line that needed review was still written, with the SKU blank and the source marked needs_review, so the work list stayed complete.

Where the rules came from

Some of the rules are facts about what the company sells, not facts about the catalog. A shaker door cannot be solid-core. When no thickness is written, a door is 1 3/8 inch, except fiberglass and 20-minute fire doors, which are 1 3/4. A few styles were discontinued, so they are reported, not resolved. Those calls came from my own purchasing and vendor knowledge, not from the code.

So the tool produced a review sheet for every wording it had seen but could not place, with the evidence next to each (which invoice, quantity and price, and which other doors fit). I filled in a decision column, a script folded the answers in, and every ruling became a new unit test. The sheets were kept with their dates and whether they had been applied or held, which gave an audit trail of what was decided and when.

Results

Unit tests only prove the code agrees with itself, so the scored runs used what the company actually billed and ordered as the answer key.

  • Worksheets against invoices. 438 of 448 doors agreed, and 378 of 390 workbooks reconciled completely. Measured 14 October 2026.
  • Purchase orders. 754 of 769 agreed line for line. Measured 14 October 2026.
  • Pre-hung doors, against billed invoice lines. 620 of 645 lines (96 percent) and 79 of 95 sheets (83 percent). Measured 16 October 2026.

These are the recorded results from those dates. I have not re-run them for this page, and I cannot show the data they ran on.

What it will not do

  • It never makes up a SKU. A door the company planned to carry reports its planned code and is never marked resolved.
  • It does not price anything. It says which door. Price books say what it costs.
  • It does not resolve hardware, sidelites or discontinued styles. Those end with a person.

I wrote these down because the alternative is a silent wrong answer. A blank SKU on a worksheet row shows up in the review list. A confidently wrong one does not.
